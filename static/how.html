How it works

Why this problem is harder than it looks

Most of the work in this project isn't the model — it's the handful of decisions that stop a tabular dataset from quietly lying to you. Leaky splits, a flattering metric, and missing values that mean something. Here's each one, and how the served app proves its own numbers.

Grouped splits, because patients repeat

Patients appear multiple times in this dataset — roughly 30,000 repeat encounters. A random row split puts the same patient in both train and test, and every score comes back inflated for a reason that has nothing to do with the model. Every split here is grouped by patient_nbr, and the code asserts the train and test patient sets don't overlap rather than trusting that they don't.

PR-AUC, because the classes are imbalanced

Only 11.4% of encounters are 30-day readmissions. Accuracy is meaningless at that base rate — predicting "no" for everyone scores 88.6% — and ROC-AUC is flattered by the large negative class. Every result in this project is reported as PR-AUC, against a dummy baseline that predicts the base rate.

Missing values that mean something

A1Cresult and max_glu_serum are 85–95% missing. But a test not being ordered is itself a signal about the encounter, so they are encoded as their own category rather than dropped or imputed away. weight, at 97% missing, is dropped — there is nothing there to encode.

Diagnoses grouped, not one-hot encoded

diag_1, diag_2 and diag_3 hold about 700 distinct ICD-9 codes each. Encoded raw that's thousands of near-empty columns; grouped into nine clinical categories — circulatory, respiratory, diabetes, and so on — it's a feature the model can actually learn from.

One more exclusion matters enough to have its own section on the model page: encounters ending in death or hospice transfer are removed as structural negatives. See About the model.

What drives the model

Permutation importance — the drop in PR-AUC when a single feature is shuffled:

FeatureDrop in PR-AUC
number_inpatient0.0795
discharge_disposition_id0.0567
number_emergency0.0099
diag_3_group0.0058

Prior hospitalizations dominate — past admissions are the strongest predictor of future ones. Discharge destination is second, which is clinically sensible: where a patient goes after release shapes whether they come back.

Every prediction is explained

Each response carries drivers: the fields moving this particular patient's risk the most, computed by one-at-a-time counterfactuals. Each field is set to its typical value (median or mode), the model is re-run, and the change in risk is reported. All 22 what-ifs go through the model in a single batch, so an explanation costs about one extra prediction. For a patient with four prior inpatient stays: 

"drivers": [
  {"feature": "number_inpatient", "value": 4, "default": 0.0, "delta": 0.100},
  {"feature": "time_in_hospital",  "value": 7, "default": 4.0, "delta": -0.051},
  {"feature": "number_emergency",  "value": 2, "default": 0.0, "delta": 0.020}
]

The method is deliberately simple, and its limitation is stated in the UI rather than hidden: fields are varied one at a time, so interactions between them are not captured. The ordering agrees with the permutation-importance table above, and a test asserts that prior inpatient stays stay the top driver — a retrain that broke that would fail CI.

Validated against SHAP

A simple explanation method is only worth shipping if you know how wrong it is. shap_compare.py computes TreeExplainer SHAP values for 2,000 held-out patients, folding one-hot columns back into their source feature, and compares them against the counterfactual drivers for the same patients.

  • Globally the two agree: Spearman rank correlation 0.70 across all 22 features, and the same top three — number_inpatient, discharge_disposition_id, diag_1_group.
  • Per patient they name the same lead driver 44% of the time, against 4.5% by chance. That gap is the cost of ignoring interactions, quantified rather than assumed.

SHAP stays out of the served image on purpose: it would add roughly 100 MB to a 512 MB container, for a method the UI can't explain in one sentence.

Accuracy is shown, not asserted

The served model is fit on the patient-grouped 80% split, and a 1,000-row sample of the untouched 20% ships with the app. At startup GET /evaluation scores that sample and groups the patients into the same low / elevated / high bands the UI uses. The result page then shows, per band, how many patients there were, what the model predicted, and how many were actually readmitted, with 95% Wilson intervals.

Observed readmission rises band by band — roughly 7% → 12% → 42% — and a test asserts that ordering, so a retrain that broke it fails CI. Intervals are wide on a sample this size, and the page says so instead of quietly rounding it away.

The form builds itself from the model

The prediction wizard is generated from GET /schema: field names, valid values and defaults all come from the fitted pipeline, not from a hand-written form, so the UI cannot drift out of sync with the model. Subgroup caveats returned with a prediction are rendered in red above the score, and three example patients let a visitor see the model react without filling in 22 fields.

The API

  • GET /schema — field names and valid values, so a client can build its form from the model
  • GET /metadata — model version and cross-validated performance
  • GET /evaluation — the held-out calibration check, by risk band
  • POST /predict — probability, baseline rate, lift, risk band, caveats and drivers
  • POST /ask — the assistant behind Ask AI, which reaches the same functions through tools

Tests and deployment

tests/test_api.py exercises the service without needing the dataset: schema/model agreement, the 422 on missing features, the subgroup caveats, and a behavioral check that more prior inpatient stays raise predicted risk — a retrained model that got that backwards would fail CI. tests/test_split.py needs the data and skips when it is absent. GitHub Actions runs the suite on every push.

The Dockerfile builds a slim image from requirements-api.txt — no plotting or download dependencies — and reads the port from PORT. Render deploys from main automatically. 

uvicorn api:app --reload --port 8000

Built with scikit-learn 1.9.0; the pickled pipeline may not load under a different version. Full reproduction steps are in the README.

Not for clinical use. This is a personal portfolio project built on data from 1999–2008. The model has not been externally validated and performs near chance for patients aged 90+.
